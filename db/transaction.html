交易管理與 ACID (Transaction Management)

掌握資料庫的心臟：並行控制、錯誤復原與隔離層級的底層邏輯。

一、 起｜生活化比喻 (概念引入)

🏦 跨年夜的銀行轉帳大混戰：
想像跨年夜時，你透過網銀轉帳 10,000 元給朋友。系統先從你的帳戶扣除一萬，正準備將錢加進朋友帳戶時，銀行伺服器突然被倒數煙火的流量給擠到當機了！如果沒有機制保護，這 10,000 元就會憑空消失。交易管理 (Transaction) 就是資料庫的「時光機與保鑣」，它保證這種跨步驟的動作「要嘛全部成功，要嘛時光倒流回轉帳前的原狀」，絕不允許錢卡在半空中的薛丁格狀態。

二、 承｜教科書級文字詳解 (Why, What, How)

在多使用者、高併發的現代應用中，我們必須探討「為什麼 (Why)」需要交易管理。如果放任多個 SQL 指令隨意穿插執行，或者容許硬體斷電在任何指令中間發生，資料庫將立刻面臨災難。這包含了兩種層面的崩潰：一是系統層面，當程式寫入到一半時系統崩潰，會留下破損、不完整的資料結構；二是邏輯層面，當數萬人同時讀寫同一筆商品庫存時，若缺乏並行控制 (Concurrency Control)，就會發生互相覆蓋資料的慘劇。因此，交易管理是維持資料庫性命交關的核心機制。

接著我們來定義「是什麼 (What)」。在資料庫系統中，交易 (Transaction) 被定義為「一組不可分割的邏輯工作單元」，它可能包含了一連串的 SELECT、UPDATE、INSERT 指令。為了讓這個工作單元具備剛才提到的防護力，學術界提出了著名的 ACID 四大特性：
1. Atomicity (原子性)：這是「All or Nothing」的保證，交易內的指令要嘛全部完成 (Commit)，要嘛全部撤銷 (Abort/Rollback)。這通常仰賴 OS 與 DBMS 的 Log 系統來實現復原 (Recovery)。
2. Consistency (一致性)：交易執行前後，資料庫必須從一個合法的一致狀態，轉移到另一個合法的一致狀態。例如：轉帳前後，兩個帳戶的總金額加總必須相等。
3. Isolation (隔離性)：雖然系統同時有成千上萬個交易在並行處理，但對任何單一交易而言，它必須感覺自己是「獨佔」系統的。其他正在執行且尚未 Commit 的交易，其內部狀態對外不可見。
4. Durability (持久性)：一旦交易成功 Commit，其對資料庫所做的變更將會永久保存在非揮發性儲存設備 (如硬碟) 中，即使下一秒伺服器爆炸斷電，資料也絕不遺失。

最後，我們來深究「如何發生 (How)」所謂的並行干擾問題，這是考研最愛考的重點。當隔離性 (Isolation) 沒有被嚴格遵守時，會產生三種經典異常：髒讀 (Dirty Read) 發生在交易 A 修改了資料但還沒 Commit，交易 B 卻跑來讀取了這個「未確認」的資料，如果交易 A 隨後 Rollback 了，交易 B 就等於讀到了一個從未真實存在過的幽靈數據。遺失更新 (Lost Update) 則是兩個交易同時讀取同一筆資料，並各自進行計算後寫回，後寫回的交易會直接覆蓋掉前一個交易的心血。而 幻讀 (Phantom Read) 則是交易 A 在進行範圍查詢時，交易 B 偷偷在該範圍內 INSERT 了一筆新資料，導致交易 A 再次查詢時，驚訝地發現多出了一筆「幻覺」般的紀錄。

四、 合｜重點標示與提點

在應付台政大的考題時，請務必把 Dirty Read 與 Lost Update 的「時序推導」練熟。考試常會給出 T1 與 T2 的交錯執行順序表 (Schedule)，要你判斷發生了什麼異常。記住：只要有讀取到 Uncommitted Data 就是髒讀；只要寫入順序導致其中一人的 Write 被默默抹除，就是遺失更新。答題時務必寫出「因為 T1 在 T2 提交前讀取了變數 X...」等完整因果推論。

📝 互動式考古題 (Exam Practice)

🎯 [交大資管 111] 請詳細解釋 ACID 特性中的「原子性 (Atomicity)」與「持久性 (Durability)」分別依賴 DBMS 的哪個子系統來實現？若發生硬體斷電，系統如何復原？
【詳細解題推導過程】

1. 實現機制對應：
- 原子性 (Atomicity)：依賴資料庫的 復原管理子系統 (Recovery Management System)。它確保交易若中途失敗，能利用 Undo 機制將所有已經變更的暫存狀態全部消除，退回交易開始前的純淨狀態。
- 持久性 (Durability)：同樣依賴 復原管理子系統 以及系統底層的 日誌系統 (Write-Ahead Logging, WAL)。它確保只要交易宣告 Commit，其對應的 Redo Log 必然已經安全寫入磁碟，永不遺失。

2. 硬體斷電的復原推導 (Crash Recovery)：
當硬體斷電並重新開機啟動資料庫時，DBMS 會啟動復原程序，掃描磁碟上的 交易日誌 (Log File)。
- Phase 1: 分析 (Analysis)：系統會找出斷電那一刻，哪些交易已經有 <T, commit> 紀錄，哪些交易只有 <T, start> 卻沒有 commit 紀錄。
- Phase 2: Redo (重做)：為了滿足「持久性」，系統會將所有已經擁有 commit 紀錄的交易，依據 Log 重新執行一次寫入動作，確保這些已提交的變更確實回到資料頁 (Data Page) 上。
- Phase 3: Undo (撤銷)：為了滿足「原子性」，系統會將那些有 start 但沒有 commit 的「未完成交易」，進行反向還原，清除它們留在磁碟上的髒資料，維持資料的一致性。
透過這套完整的 Redo/Undo 推導，DBMS 得以在災難發生後捍衛 ACID 的神聖不可侵犯。
🎯 [台大資管 109] 試以情境推導說明，何謂「遺失更新 (Lost Update)」問題？並說明為何 Read Committed 隔離層級無法防止此問題發生？
【詳細解題推導過程】

1. 遺失更新 (Lost Update) 情境推導：
假設演唱會門票系統中，某區域剩餘票數 X = 100 存於資料庫中。現在有兩個使用者 (交易 T1 與 T2) 同時要搶 1 張票。
- 時間點 t1：T1 讀取 X 的值，得到 100。
- 時間點 t2：T2 也同時讀取 X 的值，得到 100。
- 時間點 t3：T1 在自己的記憶體中計算 100 - 1 = 99，並將 X = 99 寫回資料庫。
- 時間點 t4：T2 在自己的記憶體中計算 100 - 1 = 99，並將 X = 99 寫回資料庫，隨後 T1 與 T2 皆 Commit。
結果： 兩個人都成功買到票，系統理應賣出 2 張，剩餘 98 張。但最終資料庫中 X 的值卻是 99。T1 的更新被 T2 盲目地覆蓋掉了，這就是標準的遺失更新。

2. 為何 Read Committed 無法防止？
Read Committed (已提交讀) 的防護機制是：「交易只能讀取別人已經 Commit 的資料」。
在上述情境中，時間點 t1 與 t2，T1 和 T2 讀取的 X=100 確實是早已經 Commit 好的乾淨資料，並沒有讀取到任何人的髒資料。因此，這兩個讀取動作在 Read Committed 層級下是「完全合法」且被放行的。
遺失更新的本質在於「Read-Modify-Write」這三個動作之間被其他交易插隊，而非讀取髒資料。要解決此問題，必須將隔離層級提升至 Repeatable Read (在讀取時就加上鎖定，阻止別人寫入)，或者在 SQL 語法中使用 SELECT ... FOR UPDATE 實作悲觀鎖 (Pessimistic Locking)，才能徹底阻絕遺失更新。

作業系統行程狀態 (Process State)

解密 OS 排班核心！從 5-State Model 深入解析 CPU Context Switch 與中斷處理機制。

一、 起｜生活化比喻 (概念引入)

🏥 醫院門診的看診流程：
想像你生病去大醫院看診。你在櫃檯掛號建立病歷（New），接著坐到候診區等叫號（Ready）。護士叫到你，你進診間讓醫生看病（Running）。看到一半，醫生說要驗血，請你先去抽血站等報告，此時你不能佔著診間，必須離開（Waiting/Blocked）。拿到報告後，你不能直接衝進診間找醫生，必須回到候診區重新排隊（回到 Ready）。最後看診結束，你拿藥回家，病歷銷毀歸檔（Terminated）。這就是作業系統管理行程 (Process) 的完美縮影！

二、 承｜教科書級文字詳解 (Why, What, How)

首先，我們必須探討「為什麼 (Why)」作業系統需要如此複雜的行程狀態管理？在早期的單元程式系統 (Uniprogramming) 中，記憶體裡永遠只有一個程式在執行，當它需要讀取硬碟或等待使用者輸入時，強大的 CPU 只能在原地空轉發呆，造成極大的效能浪費。為了解決這個問題，學術界提出了「多元程式規劃 (Multiprogramming)」，允許記憶體中同時存在多個程式。為了管理這些程式爭奪 CPU 資源的混亂場面，作業系統必須為每一個正在執行的程式建立一個身分證——「行程控制表 (Process Control Block, PCB)」，並時刻追蹤它們目前的執行狀態，這就是狀態模型誕生的背景。

接著我們來定義「是什麼 (What)」。一個靜靜躺在硬碟裡的 .exe 檔案只是一堆死板的程式碼，稱為「程式 (Program)」；但當它被載入主記憶體，並分配到作業系統資源準備執行時，它就成了一個擁有生命週期的「行程 (Process)」。最經典的管理模型是 5-State Model (五狀態模型)。這五個狀態分別是：剛被創建且尚未進入記憶體的「New」；已經在記憶體中萬事俱備、只欠 CPU 東風的「Ready」；正在被 CPU 執行指令的「Running」；因為等待 I/O 或某個特定事件而無法繼續執行的「Waiting (或稱 Blocked)」；以及執行完畢等待 OS 回收資源的「Terminated」。

最後，我們深入探究這些狀態「如何轉換 (How)」，這牽涉到核心的排班器 (Scheduler) 與中斷 (Interrupt) 機制。當一個 Process 在 Ready Queue 中排到最前面時，短期排班器 (Short-term Scheduler / Dispatcher) 會將 CPU 交給它，狀態轉為 Running。若這是一個分時系統 (Time-Sharing System)，當該 Process 的時間切片 (Time Quantum) 耗盡時，硬體的計時器會發出 Interrupt，強制將它踢回 Ready 狀態。另一種情況是，若該 Process 執行到一半需要讀取檔案 (I/O Request)，它會自願放棄 CPU 進入 Waiting 狀態；直到硬碟讀取完畢發出 I/O Completion Interrupt，OS 才會將它喚醒。請特別注意：被喚醒的 Process 絕對不能直接跳回 Running 狀態，它必須乖乖回到 Ready Queue 重新排隊等待 CPU。

四、 合｜重點標示與提點

在資管所的 OS 考題中，你必須極度敏銳地區分 Waiting 與 Ready 的差異。考官最愛問的陷阱是：「當 I/O 完成時，行程會轉移到哪裡？」許多新手會直覺回答 Running，這是致命錯誤！I/O 完成只代表資源到了，但 CPU 當時可能正在處理別的事情，所以只能回到 Ready 狀態排隊。另外，請務必熟記 Context Switch (內容切換) 這個關鍵字，當行程在 Ready 與 Running 之間切換時，OS 必須將舊行程的暫存器資料存入 PCB，並載入新行程的 PCB 狀態，這個動作本身是純粹的 Overhead (系統額外負擔)，這也是為何設計高效率排班演算法如此重要的原因。

📝 互動式考古題 (Exam Practice)

🎯 [交大資管 110] 當一個正在 CPU 上執行的 Process 發出 I/O 請求後，會發生什麼狀態轉換？當該 I/O 請求完成時，又會發生什麼狀態轉換？請詳細說明其背後的 OS 運作機制。
【詳細解題推導過程】

1. 發出 I/O 請求時的狀態轉換：
狀態將由 Running (執行) 轉換為 Waiting / Blocked (等待)。
底層機制推導：因為 I/O 設備（如硬碟存取）的速度遠慢於 CPU，為了不讓 CPU 原地發呆 (Busy Waiting)，該 Process 會透過 System Call 主動放棄 CPU 控制權。作業系統會介入，將該 Process 的當前狀態（如 Program Counter、Registers）儲存到它的 PCB 中，並將該 PCB 移入對應 I/O 設備的 Device Queue（等待佇列）中。接著，OS 的短期排班器會從 Ready Queue 中挑選下一個行程進入 Running 狀態，以維持 CPU 的高使用率。

2. I/O 請求完成時的狀態轉換：
狀態將由 Waiting / Blocked (等待) 轉換為 Ready (就緒)。
底層機制推導：當硬碟或外部設備完成資料讀取時，硬體控制器會發送一個「硬體中斷 (Hardware Interrupt)」給 CPU。CPU 收到中斷後，會暫停目前正在執行的其他 Process，跳轉去執行 OS 的「中斷處理常式 (Interrupt Service Routine, ISR)」。ISR 確認 I/O 已完成，便會去 Device Queue 找到原本在等待的那個 Process，將其狀態更新為 Ready，並將它移動到主記憶體的 Ready Queue 中重新排隊。請注意：它不會直接搶佔 CPU 進入 Running，必須等待短期排班器下一次的 Dispatch 決策。
🎯 [台大資管 109] 何謂「內容切換 (Context Switch)」？它與 5-State Model 的狀態轉換有何關聯？為什麼系統設計者總是希望能盡量減少 Context Switch 的時間？
【詳細解題推導過程】

1. 定義與狀態轉換的關聯：
內容切換 (Context Switch) 是指 CPU 將控制權從一個 Process 轉交給另一個 Process 的過程。在 5-State Model 中，它精準發生在 Running 狀態被中斷切換回 Ready/Waiting，以及 另一個行程從 Ready 狀態被分派 (Dispatch) 進入 Running 的交接瞬間。
在切換的當下，作業系統必須執行兩大動作：首先，將即將被換下的 Process 的當前硬體執行狀態（包含所有 CPU 暫存器內容、Program Counter 程式計數器、記憶體分頁表指標等）完整備份寫入其 PCB 中；接著，從 Ready Queue 挑選下一個要執行的 Process，讀出其 PCB，將備份的狀態全部寫回 CPU 硬體暫存器中，恢復其執行環境。

2. 為何需要盡量減少 Context Switch 的時間？
因為 Context Switch 對於使用者程式而言，是一個純粹的系統額外負擔 (Pure Overhead)。在 OS 進行暫存器狀態的儲存與載入、更新記憶體管理單元 (MMU) 快取表等動作的期間，CPU 完全沒有在執行任何有生產力的 User-level 程式碼。如果 Context Switch 的時間過長，或者因為排班演算法的 Time Quantum 切得太細碎導致切換過於頻繁（發生所謂的 Thrashing），系統絕大部分的運算能力都會被耗費在「切換狀態」上，導致系統整體吞吐量 (Throughput) 嚴重下降。因此，現代硬體與 OS 通常會提供多組硬體暫存器或優化的記憶體架構，以極小化這段毫無生產力的真空時間。

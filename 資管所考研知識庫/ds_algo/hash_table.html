雜湊表 (Hash Table)

打破極限的 O(1) 搜尋神兵，詳解 Hash Function 原理與碰撞解決方案。

一、 起｜生活化比喻 (概念引入)

🗄️ 擁有神祕公式的超級圖書館員：
在傳統圖書館找書，你要嘛一排一排慢慢看 (線性搜尋)，要嘛按照編號區間跳著找 (二元搜尋)。但想像有一位超級館員，當你報出書名「哈利波特」時，他在腦中套用了一個神祕的數學公式算了一下，0.1秒後直接告訴你：「這本書在第 5 排第 3 格」，你走過去一拿，果真在那裡！雜湊表 (Hash Table) 就是這套神祕系統，它不跟你比大小，而是直接把「資料」算成「記憶體座標」，實現夢幻般的 O(1) 一步到位搜尋。

二、 承｜教科書級文字詳解 (Why, What, How)

首先探討「為什麼 (Why)」我們需要雜湊表？在軟體開發中，我們極度渴望能有 O(1) (常數時間) 的超高速搜尋。陣列 Array[index] 雖然能做到 O(1)，但前提是你的「鍵值 (Key)」必須是連續的小整數。如果我們要查詢的使用者帳號是字串 "john_doe"，或者是身分證字號這種極大的稀疏數字，我們不可能宣告一個長度無限大的陣列來對應。我們需要一種機制，能將龐大、不規則的 Key，壓縮並映射到一個有限、可控的連續記憶體空間中，這就是雜湊表存在的價值。

接著解析「是什麼 (What)」構成了這套系統。雜湊表的核心靈魂是 雜湊函數 (Hash Function)。這個數學函數就像一台果汁機，你丟入任何長度與型態的 Key，它都會攪碎並運算出一組固定範圍的整數，我們稱為 Hash Value 或 Hash Code。拿到這個整數後，我們將其作為陣列 (通常稱為 Bucket Array) 的 Index，把資料直接存進去。一個優良的 Hash Function 必須具備「運算極快」、「結果具有確定性 (同樣的 Key 必定算出同樣的 Hash)」以及「分佈均勻 (Uniform Distribution)」三大特質，盡可能讓不同的 Key 散佈在陣列的不同角落。

最關鍵的是「如何處理異常 (How to handle Collisions)」。這牽涉到鴿籠原理 (Pigeonhole Principle)：既然我們的陣列空間是有限的，而潛在的 Key 組合是無限的，那必定會發生「兩個不同的 Key，被算出完全一樣的 Hash Value，搶同一個陣列格子」的慘劇，這在學術上稱為 碰撞 (Collision)。為了處理碰撞，科學家發展出兩大派別：第一派是 Chaining (鏈結法)，既然格子塞不下，我們就在那個格子外掛一條 Linked List 鏈結串列，所有撞在同一格的資料都串在一起；第二派是 Open Addressing (開放定址法)，堅持所有的資料都必須存放在陣列本體內，如果這格被佔走了，就按照某種探測規則 (Probing) 往陣列的下一個空位找，直到找到為止。

碰撞解決策略 (Collision Resolution) 深度對照表

策略類別具體方法名稱運作邏輯推導致命缺點與效能瓶頸
外部串接 Chaining (鏈結法) 每個陣列槽位(Bucket)存放一個指標，指向一條 Linked List。發生碰撞時，直接將新元素加到對應 List 的尾端。 當發生嚴重碰撞時，List 會變得很長，搜尋時間從 O(1) 退化為 O(n)。且需額外記憶體儲存指標 (Pointers)。
開放定址 (Open Addressing) Linear Probing (線性探測) 發生碰撞時，依序檢查下一個位置：H(x)+1, H(x)+2... 直到找到空位。 會引發嚴重的 一次群聚 (Primary Clustering)。佔用相鄰空位會導致接下來更容易發生連鎖碰撞，效能急速惡化。
Quadratic Probing (平方探測) 跳著找空位，檢查 H(x)+1², H(x)+2², H(x)+3²...，試圖打散連續佔用的區塊。 雖然解決了一次群聚，但若兩個 Key 最初的 Hash 相同，它們的探測路徑仍會完全重疊，引發 二次群聚 (Secondary Clustering)。
Double Hashing (雙重雜湊) 準備兩個 Hash Function。碰撞時，將第二個函數的結果作為「步長 (Step Size)」跳躍尋找空位。 因為每個元素的第二 Hash 值不同，跳躍步伐也不同，完美打散了群聚效應。是 Open Addressing 中效能最優雅的解法。

四、 合｜重點標示與提點

在研究所考試中，除了考碰撞機制的追蹤外，另一個超級重點是 負載因子 (Load Factor, 通常符號為 α)。它的公式是 α = 總元素數量 (n) / 陣列大小 (m)。當 Load Factor 越來越高，代表陣列越來越擁擠，碰撞機率指數上升，O(1) 的效能將徹底崩盤。此時，系統必須觸發 Rehashing (重新雜湊) 機制，也就是宣告一個通常是原本 2 倍大 (且最好是質數) 的新陣列，並把所有舊資料重新計算 Hash 搬家過去，這個耗時的動作是維持 Hash Table 高效運作的必要之惡。

📝 互動式考古題 (Exam Practice)

🎯 [交大資管 109] 給定一個大小為 7 的 Hash Table (索引 0~6)，使用 Hash Function `H(k) = k mod 7`。依序插入資料 `15, 22, 29, 8`。若系統採用「線性探測 (Linear Probing)」解決碰撞，請詳細推導每筆資料最終寫入的索引位置。
【詳細解題推導過程】

我們一步步推導每一次的插入動作與探測軌跡：

1. 插入 15：
計算 H(15) = 15 mod 7 = 1。
檢查 Bucket[1]，是空的。
直接存入。目前表格狀態：[空, 15, 空, 空, 空, 空, 空]

2. 插入 22：
計算 H(22) = 22 mod 7 = 1。
檢查 Bucket[1]，發現已經被 15 佔走了 (發生碰撞 Collision)！
啟動 Linear Probing，往下一格探測：檢查 Bucket[1+1] = Bucket[2]。
Bucket[2] 是空的，存入 22。目前表格狀態：[空, 15, 22, 空, 空, 空, 空]

3. 插入 29：
計算 H(29) = 29 mod 7 = 1。
檢查 Bucket[1]，被佔走 (碰撞)。
啟動 Linear Probing：
探測 Bucket[2]，被 22 佔走 (碰撞)。
探測 Bucket[3]，是空的。
存入 29。目前表格狀態：[空, 15, 22, 29, 空, 空, 空]。
(注意：這就是典型的 Primary Clustering 一次群聚，15, 22, 29 擠成了一團！)

4. 插入 8：
計算 H(8) = 8 mod 7 = 1。
檢查 Bucket[1]，被佔走 (碰撞)。
啟動 Linear Probing：
探測 Bucket[2]...有資料。
探測 Bucket[3]...有資料。
探測 Bucket[4]，終於是空的。
存入 8。最終表格狀態：[空, 15, 22, 29, 8, 空, 空]

【最終解答】
15 位於 Index 1
22 位於 Index 2
29 位於 Index 3
8 位於 Index 4
🎯 [政大資管 111] 何謂 Load Factor (負載因子)？在 Java 的 HashMap 底層實作中，當發生嚴重的 Hash Collision 導致特定 Bucket 的 Chaining Linked List 過長時，會觸發什麼樣的結構轉變來維持搜尋效能？
【詳細解題推導過程】

1. 負載因子 (Load Factor) 定義：
負載因子 α = Table中已存放的元素總數 (n) / Table 的總槽位數 (m)。
它是一個衡量 Hash Table 擁擠程度的指標。當 α 越大，代表資料越滿，發生碰撞的機率急遽攀升。實務上 (如 Java)，當 α 超過預設閾值 (通常是 0.75) 時，系統就會不惜付出巨大代價執行 Rehashing，將 Table 擴容 2 倍，以重新降低碰撞機率。

2. Java HashMap 底層的鏈結串列優化 (Treeify 機制)：
即使 Load Factor 保持在正常範圍，若 Hash Function 設計不良或面臨駭客惡意塞入大量 Hash 同餘的 Key (Hash DoS 攻擊)，仍會導致某個單一 Bucket 發生極度嚴重的碰撞。在傳統的 Chaining 實作中，這個 Bucket 會長出一條超長的 Linked List，導致該 Bucket 內的搜尋效能退化成悲劇的 O(n)。
為了解決這個極端狀況，Java 8 之後的 HashMap 導入了結構轉變機制：
當單一個 Bucket 內的 Linked List 節點數量 大於等於 8 (且總 Table 容量大於等於 64) 時，系統會啟動 Treeify 動作，將這條單向鏈結串列，直接轉換重構成一棵 紅黑樹 (Red-Black Tree)。
這個偉大的改良，確保了即使在最極端、所有 Key 都撞在同一格的 Worst Case 下，Hash Table 的搜尋效能底線依然能被紅黑樹的 O(log n) 給守住，不會徹底崩潰。
